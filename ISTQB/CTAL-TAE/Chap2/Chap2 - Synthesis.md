### Keywords

| Term | Definition |
| --- | --- |
| **API Testing** | Testing performed by submitting commands to the software under test using programming interfaces of the application directly. |
| **GUI Testing** | Testing performed by interacting with the software under test via the graphical user interface. |
| **Testability** | The degree of effectiveness and efficiency with which test conditions can be established for a component or system, and tests can be performed to determine whether those conditions have been met. |

## 2.1 Understand the Configuration of an Infrastructure to Enable Test Automation

### TAE-2.1.1 (K2) Describe the configuration needs of an infrastructure that enable implementation of test automation

Testability is the availability of software interfaces that support testing, especially control and observability of the SUT (system under test). It should be designed and implemented alongside other SUT features, not bolted on later. An SA (software architect) usually owns this non-functional requirement, with input from the TAE (test automation engineer) on where improvements matter most.

#### Solutions for better testability

Different solutions imply different configuration needs:

| Solution | Idea | Configuration note |
| --- | --- | --- |
| Accessibility identifiers | Unique IDs on UI elements so automation can find them reliably | Generated by a framework or set manually by developers (manual is often more reliable) |
| System environment variables | Application parameters changed via administration to make testing easier | e.g. enable a "test mode" that makes behaviour more predictable |
| Deployment variables | Similar to system variables, but set before deployment | e.g. point the app at a test database instead of production |

**Example:** a project without accessibility identifiers relied on brittle XPath selectors that broke constantly. After identifiers were added, testability improved sharply.

#### Key aspects of designing for testability

1. **Observability:** the SUT exposes interfaces that show internal behaviour (like putting windows on a black box to see what is going on inside). Test cases use them to compare actual vs expected results.
2. **Controllability:** the SUT exposes interfaces to perform actions (UI elements, function calls, protocols such as TCP/IP or USB, electronic signals for physical or logical switches). Without control, observation alone is not enough to test.
3. **Architecture transparency:** documentation makes components and interfaces clear, so observability and controllability exist at every test level and quality is easier to sustain.

**Example:** a banking app added logging endpoints so testers could monitor transactions behind the scenes and verify results more reliably.

#### Why it matters

| Without testability | With testability |
| --- | --- |
| Automated tests are fragile, unreliable, and hard to maintain | Reliable tests, meaningful results, less manual work |
| Tests break often on SUT change; time goes to fixing tests, not finding defects | Investing early saves more later ("pay now, or pay much more later") |

#### Conclusion (2.1.1)

1. Design and implement testability alongside the other SUT features so automation is not fragile, unreliable, or expensive to maintain later.
2. Use accessibility identifiers, system environment variables, and deployment variables to make the SUT easier to find, control, and configure for automated runs.
3. Cover observability, controllability, and architecture transparency so tests can see results, drive actions, and work at every test level with a clear system map.

### TAE-2.1.2 (K2) Explain how test automation is leveraged within different environments

Different automated tests run in different environments. Environments vary by project and methodology; technically they may use containers, virtualization, cloud platforms, or on-premise servers. Understanding each environment's purpose is essential for an effective automation strategy.

**Example:** five environments (Dev, QA, UAT, Staging, Production), each with a clear role, made automation more effective once purpose and ownership were clear.

#### Local development environment

On the developer's machine. Used to create and run automated component, GUI, and API tests as a first line of defence. With an IDE (e.g. Visual Studio, IntelliJ), white-box testing is possible: step through code and run unit tests early.

#### Build environment

A local setup or a CI/CD agent (e.g. Jenkins, GitLab, Bitbucket) in a DevOps pipeline. Main goal: build the software and run low-level checks without deploying elsewhere: component tests, component integration tests, and static analysis.

**Example:** every push triggered a Bitbucket pipeline that built the code and ran unit tests; failures emailed developers.

#### Integration environment

A deployment environment with a fully integrated release candidate of the SUT. Runs UI and/or API suites as users would. Black-box only (system integration and/or acceptance). First place where monitoring (logs, API calls, DB queries) should be present so failures can be investigated efficiently.

#### Pre-production / staging / UAT environment

A deployment environment that resembles production as closely as possible. Focus on non-functional quality (performance, load, security, usability, etc.) and often stakeholder acceptance testing. Existing automated suites can be reused here. Monitoring remains critical.

#### Production / operational environment

Where end users interact with the system. Functional and non-functional behaviour can be assessed in real time using practices such as:

- **Canary release:** roll out a feature to a small user subset first
- **Blue/green deployment:** keep two environments; deploy to the idle one, then switch traffic
- **A/B testing:** run two variants and compare outcomes (e.g. a search feature to 5% of users)

#### End-to-end example

New recommendation feature on an e-commerce site:

1. **Local:** developers write the algorithm and unit tests on purchase-history cases
2. **Build:** CI/CD builds and runs unit tests so existing behaviour is not broken
3. **Integration:** automated checks that recommendations appear, clicks navigate correctly, and the API returns the right format
4. **Pre-production:** performance checks that recommendations do not slow the page; stakeholders review business sense
5. **Production:** roll out to 10% of users, measure engagement, then widen if results are positive

#### Conclusion (2.1.2)

1. Leverage automation across multiple environments, each with a clear purpose.
2. Typical split: local (early), build (code validation), integration (full-system black-box), pre-production (non-functional / acceptance), production (real-world validation).
3. Match test placement to environment purpose to catch defects earlier; avoid running tests with no clear home.

## 2.2 Evaluation Process for Selecting the Right Tools and Strategies

### TAE-2.2.1 (K4) Analyze a system under test to determine the appropriate test automation solution

Every SUT is unique. The TAS must follow the system's specificities and constraints, not a one-size-fits-all template. Analyze type of application, stack, interfaces (UI, API), testability, integrations, and risks. Gather requirements with both scope (what to automate, which products/lifecycle) and capabilities (skills, data, environments, tools) in mind. Different application types (web service, mobile, web) need different technical automation approaches.

Do not analyze alone. Collaborate with manual testers (day-to-day testing challenges), business stakeholders (business risk), and business analysts (requirements depth) to surface risks and mitigations early.

**Example:** missing the business analyst in automation planning omitted critical business logic; a large part of the framework had to be rewritten later.

**Example:** a web-service backend needed API-focused tools; a mobile banking app needed tools that simulate touch and support mobile features.

#### Requirements to consider

Ask these questions when shaping the TAS approach and architecture:

| Area | Ask | Used to decide |
| --- | --- | --- |
| Test process activities | Which activities should be automated: test management, test design, test generation, and/or test execution? | Where automation effort goes in the test process |
| Test levels | Which levels must the TAS support: component, integration, system, acceptance? | How deep and where automation sits in the test pyramid |
| Test types | Which types must be supported: functional, performance, security, usability, etc.? | Which tools or approaches are needed (types often need different tools) |
| Roles and skills | Who will create and maintain the automated tests, and what programming / automation skills do they have? | Whether a coded framework, low-code, or mixed approach is realistic |
| Products and lifespan | Which products, product lines, or families must be supported, and how long should the TAS last (including multi-version support)? | Scope and durability of the investment |
| SUT compatibility | What kinds of SUT must the TAS work with (web, mobile, desktop, etc.), and through which interfaces (GUI, API, or both) and technologies? | Technical stack and tool family |
| Test data | Are suitable test data available and of good quality? Can data be generated? Are there privacy or security constraints? | Data strategy before scripting |
| Edge cases and third parties | How will unreachable cases be emulated, and how will third-party or unavailable external systems be handled (mock, stub, simulator)? | Feasibility of high-risk or external dependencies |

**Examples of trade-offs**

- Regulated healthcare may need strong test-management automation for compliance; a startup may prioritise fast execution and feedback.
- One project focused system-level automation where most regressions lived; another focused component level for faster feedback.
- A complex coded framework failed in practice when most testers lacked programming skill.
- In healthcare, building realistic anonymised test data cost almost as much as the automation itself.
- Payment processors may require mocks or simulations instead of real card transactions in automated runs.

#### Practical approach

1. Document the SUT architecture (components, interfaces, technologies)
2. Map key user journeys
3. Identify high-risk areas
4. Assess technical feasibility of automation per area
5. Consider resource constraints (budget, time, expertise)
6. Build a prioritised automation roadmap from risk, feasibility, and constraints

**Example:** retail point-of-sale with touchscreen, inventory, and payments. Analysis showed payment was highest business risk but hard to automate; inventory APIs were straightforward; the custom touchscreen UI had limited automation support. Decision: start with inventory API automation (easy wins), simulate payments (high risk), and keep a limited UI suite on critical paths only.

Goal: automate the right things the right way for value, not everything.

#### Conclusion (2.2.1)

1. Treat each SUT as unique; derive the TAS from its constraints.
2. Collaborate with stakeholders to find risks and requirements.
3. Cover activities, levels, types, skills, product scope, SUT compatibility, data, and third-party/edge strategies.
4. Prioritise by risk, feasibility, and constraints.

### TAE-2.2.2 (K4) Illustrate the technical findings of a tool evaluation

After SUT analysis and stakeholder requirements, candidate tools can be considered. No single tool may cover every need; stakeholders should accept that. Capture findings in a **comparison table**: tools as columns, requirements as rows, cells with how each tool meets each requirement plus priority. The table is the basis for proposing a tool or tool set.

#### Sample comparison table

| Requirement (priority) | Tool A | Tool B | Tool C |
| --- | --- | --- | --- |
| JavaScript support (high) | Excellent | Good | Limited |
| Cross-browser testing (high) | All major browsers | Chrome & Firefox only | All major browsers |
| Mobile testing (high) | Limited | Excellent | Good |
| Reporting capabilities (high) | Basic | Comprehensive | Customizable |
| Learning curve (medium) | Steep | Moderate | Gentle |
| Cost (high) | $$$ | $$ | Free / open source |

#### Key requirements to assess

| Requirement | What to check |
| --- | --- |
| Language / technology and IDE | Tool language vs team skill; IDE integration |
| Configuration flexibility | Multiple environments, easy config runs, static vs dynamic values |
| Test data management | Import, data-driven testing, version control / central repository |
| Support for test types | Functional, performance, security, accessibility; a suite of specialised tools is fine if they integrate |
| Reporting | Automated generation, customisation, readable for non-technical stakeholders |
| Integration with other tools | CI/CD, task tracking, test management |
| Overall architecture fit | Scalability, maintainability, modifiability, compatibility, reliability |

**Examples**

- A Python team picking a C# tool stalled for months until they switched to a Python tool.
- YAML configuration made environment changes fast.
- CSV-driven product scenarios let business analysts update data without editing code.
- Healthcare: WebdriverIO (UI), JMeter (performance), OWASP ZAP (security).
- HTML reports with failure screenshots and trends let PMs assess health without asking the test team.
- Strong GitHub Actions integration enabled tests on every pull request.

#### Creating an effective comparison table

- Assess objectively (facts, not preference)
- Use a clear scale (e.g. Excellent / Good / Fair / Poor, or 1–5)
- Add context to ratings so stakeholders know what "good" means here
- Weight requirements by importance
- Look 1–2 years ahead, not only today

**Example:** a tool fitted immediate needs but could not extend; six months later the team had to switch and lost prior work.

#### Decision process

1. Filter on must-have requirements
2. Score remaining tools (rating × weight)
3. Sum totals
4. Consider intangibles when scores are close (vendor, community, roadmap)
5. Draft a proposal for a tool or tool set
6. Present findings to stakeholders for approval

**Example:** two tools scored similarly; the deciding factor was a more active open-source community and frequent updates.

#### Proof of concept

Before the final decision, run a POC: implement sample cases, run them in a real environment, evaluate against criteria. Documentation alone often misses issues or strengths.

**Example:** a POC rejected the first choice because it handled custom JavaScript poorly; the second tool handled it well and avoided a bad commitment.

#### Case study

Web app: Angular frontend + REST API. Priorities included UI+API support, learning curve for non-coders, management reporting, Azure DevOps CI/CD, and cost for a team of ten.

| Requirement (priority) | Selenium + RestAssured | Cypress | TestComplete |
| --- | --- | --- | --- |
| UI + API testing (high) | Good (separate tools, work well together) | Excellent (integrated) | Fair (UI-focused, limited API) |
| Learning curve (high) | Steep (solid Java needed) | Moderate (JS helpful, not mandatory) | Gentle (low-code) |
| Reporting (medium) | Basic (needs extensions) | Good (built-in dashboard) | Excellent (visual reports) |
| Azure DevOps CI/CD (high) | Excellent (native) | Good (some configuration) | Good (some configuration) |
| Cost (medium) | Free (open source) | Free for basic use | Expensive (per-seat) |

After scoring and discussion, the team chose Cypress. Selenium was dropped for training cost; TestComplete for price and weak API support.

#### Conclusion (2.2.2)

1. Use a comparison table to make evaluation visible.
2. Assess language/IDE fit, configuration, data handling, test types, reporting, integrations, and architecture qualities.
3. Weight requirements realistically and look ahead.
4. POC the top contenders.
5. Present a clear proposal for stakeholder approval; there is no perfect tool.

## Chapter wrap-up

1. Build testability into the SUT early (identifiers, variables, observability, controllability, transparency).
2. Place automation where each environment adds the right feedback.
3. Analyze the SUT with stakeholders and prioritise what to automate.
4. Evaluate tools with a weighted comparison table, POC, and approved proposal.
